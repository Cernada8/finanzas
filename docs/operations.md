# Operations

## Environments

Two Postgres databases are supported (see `docs/architecture.md#workspace-isolation`):
`DATABASE_URL` for real data, `DATABASE_URL_DEMO` for the isolated demo workspace. `WORKSPACE_MODE`
(`demo` | `live`) picks which one a given process (dev server, seed script) talks to. Never point
both env vars at the same database. On the production Vercel deployment, `WORKSPACE_MODE=live` is
the default and `DATABASE_URL_DEMO` is normally left unset — see below.

## Deploying to Vercel + Supabase

This is the supported production path: Vercel hosts the Next.js app, Supabase hosts the Postgres
database that Prisma talks to. The app never uses the Supabase client SDK, PostgREST, or the
anon/service-role API keys — it connects straight to Postgres via Prisma, exactly like any other
hosted Postgres. Supabase's other product surfaces (Auth, Storage, Edge Functions, the
autogenerated REST API) are unused.

### 1. Database (Supabase)

A dedicated Supabase project holds the schema (already applied for this build — see the project's
`id`/`ref` you were given). Supabase exposes two Postgres connection strings under **Project
Settings -> Database -> Connection string**:

- **Pooled** (port 6543, "Transaction" mode, `?pgbouncer=true`) — this is `DATABASE_URL`, what the
  app uses at request time. Required on Vercel: serverless functions open/close connections
  constantly and would exhaust Postgres's direct connection limit without the pooler.
- **Direct** (port 5432, no pgbouncer) — this is `DIRECT_URL`, used only by `prisma migrate deploy`.
  The pooler runs in transaction mode and doesn't support the session-level features migrations
  need.

`prisma/schema.prisma`'s `datasource db` block declares both (`url` / `directUrl`); nothing else in
the schema changes between local Postgres and Supabase.

The database password is set once, at project creation, and is only ever shown to you in the
Supabase dashboard (**Project Settings -> Database -> Connection string**, or reset it there) — it
is not retrievable through the Supabase API/MCP tooling used to provision the project, by design.
Grab it from the dashboard and substitute it into both connection strings below.

### 2. Environment variables (set these in the Vercel project settings)

```
WORKSPACE_MODE=live
DATABASE_URL=postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:6543/postgres?pgbouncer=true
DIRECT_URL=postgresql://postgres:<password>@db.<project-ref>.supabase.co:5432/postgres
NEXTAUTH_SECRET=<openssl rand -base64 32>
NEXTAUTH_URL=https://<your-vercel-domain>
AUTH_TRUST_HOST=true
APP_ENCRYPTION_KEY=<openssl rand -base64 32>
APP_ENCRYPTION_KEY_VERSION=1
```

Leave every `*_PSD2_*` / `POWENS_*` variable unset unless you've actually obtained credentials for
one of those providers (see `docs/integration-feasibility.md`) — the app runs fully in
demo/import-only mode without them.

`NEXTAUTH_URL` must exactly match the domain Vercel serves the app on (the `*.vercel.app` URL, or
your custom domain once attached) — mismatches surface as an `UntrustedHost` auth error, and
changing it requires a redeploy since Next.js bakes some of this into the build.

### 3. Apply the schema and create your login

Run once, from your own machine, pointed at the Supabase **direct** connection string (the pooler
doesn't support `prisma migrate deploy`):

```bash
DATABASE_URL="$DIRECT_URL" npx prisma migrate deploy
WORKSPACE_MODE=live npx tsx prisma/seed/create-owner.ts you@example.com "strong-password" "Your Name"
```

(`create-owner.ts` reads `DATABASE_URL`/`WORKSPACE_MODE` the same way the deployed app does — see
`src/lib/prisma.ts`.) This creates the single owner row you'll log in with; there is no public
signup route.

### 4. Vercel project settings

- **Build command**: default (`next build`) is fine — `postinstall: prisma generate` in
  `package.json` ensures the Prisma client is generated before the build step runs.
- **Framework preset**: Next.js (auto-detected).
- **Node version**: 20.x or later.
- No `vercel.json` is required.

### 5. Demo workspace

`WORKSPACE_MODE=demo` needs its own, separate database (`DATABASE_URL_DEMO`) — mixing demo and real
data in one database is exactly what the two-database design in
`docs/architecture.md#workspace-isolation` exists to prevent. The production Vercel deployment
doesn't need one; if you want a hosted demo too, create a second Supabase project, apply the same
migration to it, and set `DATABASE_URL_DEMO` (Vercel doesn't let one deployment switch
`WORKSPACE_MODE` per-request, so a hosted demo in practice means a second Vercel deployment/branch
with `WORKSPACE_MODE=demo` and its own env vars, not a toggle in the running app).

### Row Level Security note

Supabase's dashboard will flag every table with "RLS disabled." This is expected and safe **for
this app's access pattern**: nothing here uses the Supabase anon/service-role API keys or
PostgREST — Prisma connects directly as the `postgres` role over the connection strings above, so
Postgres's own role-based access (not RLS policies meant for the anon/authenticated PostgREST
roles) is what's actually gating access. RLS would only matter if you additionally exposed these
tables through Supabase's autogenerated REST/GraphQL API, which this build never does. Leave it
disabled unless you plan to use that API surface too.

## Running locally

```bash
npm install
npx prisma migrate deploy                                            # against DATABASE_URL
DATABASE_URL="$DATABASE_URL_DEMO" npx prisma migrate deploy           # against DATABASE_URL_DEMO
WORKSPACE_MODE=live  npx tsx prisma/seed/create-owner.ts you@example.com "strong-password" "Name"
WORKSPACE_MODE=demo  npx tsx prisma/seed/demo-seed.ts                 # creates owner + syncs demo data
npm run dev
```

## Secrets

`NEXTAUTH_SECRET`, `APP_ENCRYPTION_KEY` (32 bytes, base64 — `openssl rand -base64 32`), and any
provider client secrets must never be committed. `.env.example` documents every variable; `.env` /
`.env.local` are gitignored by the create-next-app default `.gitignore`. In a real deployment,
source `APP_ENCRYPTION_KEY` from a KMS or secret manager rather than a flat file — the application
code only needs the raw key bytes at runtime, so this is an infrastructure choice, not a code
change.

### Key rotation

`Connection.tokenCipherVersion` records which `APP_ENCRYPTION_KEY_VERSION` encrypted each stored
token. To rotate: (1) generate a new key, set it as the *new* `APP_ENCRYPTION_KEY` and bump
`APP_ENCRYPTION_KEY_VERSION`; (2) extend `src/lib/crypto.ts` to accept a map of
`{ version: keyBytes }` for decryption while always encrypting with the current version (not yet
implemented — today there is one active key, matching that no live adapter yet stores a token); (3)
run a one-off script that reads every `Connection`, decrypts with its recorded version, re-encrypts
with the current one, and updates `tokenCipherVersion`.

## Backup & restore

This build does not implement automated backups — that's an infrastructure/hosting decision the
brief explicitly says needs the user's approval (§7: "Choose production region and infrastructure
only after the user approves hosting and cost"). Until then, for local/self-hosted use:

```bash
# Backup (run against whichever database you're backing up)
pg_dump --format=custom "$DATABASE_URL" > backup-live-$(date +%F).dump

# Restore into a fresh database
createdb spending_dashboard_restored
pg_restore --dbname=spending_dashboard_restored backup-live-2026-09-17.dump
```

Test a restore periodically by actually running the restore command above into a scratch database
and spot-checking a few known transactions/holdings — an untested backup is not a backup.

## Data export & deletion (brief §7)

Not yet wired to a self-service UI button (see `app/settings/page.tsx`) — implemented as operator
scripts against the `Owner`'s data, run by whoever administers the deployment (which, for this
single-owner app, is the owner themselves via the CLI):

- **Export**: query every table filtered by `ownerId` and write to JSON. A `prisma/seed`-style
  script following the same pattern as `demo-seed.ts` (iterate models, `findMany({ where: {
  ownerId } })`, serialize `BigInt`/`Decimal` fields to strings) is the natural place to add this;
  it is not implemented in this delivery — flagged here as a known gap rather than silently
  omitted.
- **Connection revocation**: set `Connection.status = DISCONNECTED` and clear
  `encryptedAccessToken` / `encryptedRefreshToken`. No live adapter currently stores tokens, so
  there is nothing to revoke yet in practice.
- **Deletion**: `Owner` cascades (`onDelete: Cascade`) to every owned row in the schema (accounts,
  transactions, holdings, imports, audit events, sessions) — deleting the `Owner` row deletes
  everything. This does **not** touch database backups already taken (per brief §7, that must be
  documented rather than silently implied) — a full erasure additionally requires deleting or
  expiring any backup snapshots that contain the deleted owner's data, per your backup retention
  policy.

## Logging & redaction

`src/lib/crypto.ts#redactForLog` strips anything that looks like a token (long alphanumeric runs,
`Bearer <token>`) before an error is written to `Connection.lastErrorRedacted` or
`SyncRun.errorRedacted`. Application logs should never include full request/response bodies from a
provider call; adapters in this build (only `DemoAdapter`) never log payloads at all.

## Known gaps in this delivery (stated plainly, not hidden)

- No production infrastructure, hosting, TLS termination, or CI/CD is set up — local-only by
  design, pending the user's explicit choice per brief §7.
- No self-service data export/deletion UI (see above) — script-level only.
- No webhook receiver (no live adapter emits webhooks yet, so there's nothing to verify signatures
  against; `docs/architecture.md` notes where that would go).
- The import UI is a single-step auto-detect-and-commit flow, not the fully interactive
  column-mapping wizard described in the brief (see `docs/architecture.md#import-pipeline`).
- Key rotation is designed but not implemented end-to-end (see above).
